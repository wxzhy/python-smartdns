# 需求与功能说明（简化版）

本文档用于迁移或重写本项目时快速理解业务需求和主要处理过程。它刻意不描述具体代码结构、函数名或库调用细节，只保留系统应具备的能力、处理顺序和关键边界。

## 1. 项目目标

本项目要实现一个可扩展的本地 DNS 转发器。它接收客户端 DNS 查询，根据配置、标签、规则和插件逻辑选择合适的上游解析器，并返回可被插件缓存、记录、过滤或改写后的 DNS 响应。

核心目标：

- 支持本地 DNS 代理场景，可接收 UDP、TCP 和可选 DoH 查询。
- 支持多个上游解析器和上游分组。
- 支持按标签、查询类型等条件进行规则分流。
- 支持插件在请求前、上游响应后、最终响应前后介入处理。
- 支持缓存、查询日志、拦截、重定向、IP 过滤、IP 替换、测速和 HTTPS 记录处理等扩展能力。
- 使用单一配置文件描述运行时、监听器、上游、规则、插件和 WebUI。
- 提供可选 WebUI，用于查看状态、编辑配置、手动 reload 和查看查询日志。

## 2. 使用场景

典型使用场景：

- 本机或局域网 DNS 代理。
- 按域名、IP 标签或查询类型选择不同 DNS 上游。
- 对特定域名返回静态结果或重定向到另一个域名。
- 对解析结果进行缓存、测速、过滤或改写。
- 观察 DNS 查询日志，辅助调试规则和上游质量。
- 对 HTTPS 记录进行清洗或补充特定参数。

## 3. 功能范围

### 3.1 DNS 接入

系统应支持：

- UDP DNS 查询。
- TCP DNS 查询。
- 可选 DoH 查询。
- 对非法 DNS 请求返回格式错误响应，或按协议要求拒绝请求。

DNS 接入层只负责协议适配：接收 wire 数据、解析为 DNS 消息、交给统一处理流程、再把响应编码返回。接入层不应包含规则选择、插件逻辑或上游解析策略。

### 3.2 配置管理

系统使用单一配置文件。配置至少应包含：

- 运行时参数。
- DNS 监听器。
- 上游 nameserver。
- upstream。
- upstream group。
- 分流规则。
- 插件列表和插件参数。
- WebUI 参数。
- 域名标签文件目录和 IP 标签文件目录。

配置加载时应完成基础校验：

- 名称不能重复。
- 引用对象必须存在。
- 默认上游组必须存在。
- 上游组不能形成循环引用。
- 插件配置必须能被对应插件识别。
- 配置不足以启动服务时应尽早失败。

### 3.3 上游解析

系统应支持多个上游协议或上游实现。每个 upstream 可以包含一个或多个 nameserver，并定义超时、生命周期、是否使用 TCP、ECS 等参数。

上游按两层组织：

- upstream：实际可执行查询的上游单元。
- upstream group：由 upstream 或其他 group 组成的逻辑分组。

group 可以嵌套，但不能循环。

### 3.4 调度策略

系统至少支持两种调度策略：

- 竞速返回：同时请求多个目标，返回第一个成功结果。
- 等待全部：等待多个目标全部完成，从成功结果中选择最快或最合适的结果，同时保留全部结果供后续插件使用。

当所有上游失败时，系统应返回可解释的失败结果。若失败中包含 NXDOMAIN，应优先保留 NXDOMAIN 语义。

### 3.5 规则分流

规则用于选择 upstream group 和调度策略。

规则匹配条件至少包括：

- 请求标签。
- 排除标签。
- 查询类型。

规则按配置顺序匹配，命中第一条可用规则后停止。没有规则命中时使用默认上游组和默认调度策略。

规则选择只依赖请求阶段已经得到的标签，不依赖上游响应后才产生的标签。

### 3.6 插件扩展

插件用于扩展主处理流程。插件应能在以下阶段介入：

- 请求阶段：查询到达后、规则选择前。
- 上游响应阶段：每个上游结果返回后。
- 响应阶段：最终响应返回客户端前。
- 观测阶段：最终响应确定后，用于日志、指标、审计。
- 收尾阶段：无论处理成功或失败都执行，用于清理和兜底。

插件应支持：

- 独立配置。
- 独立运行时变量。
- 注册共享服务。
- 注册每个请求独立的上下文。
- 注册自定义 resolver。
- 注册响应构造器。

插件私有状态不应直接塞进核心请求对象，应通过插件上下文保存，避免核心模型膨胀，也避免并发请求互相污染。

### 3.7 WebUI

WebUI 是可选能力，应支持：

- 查看当前运行状态。
- 查看监听器、上游、规则和插件摘要。
- 查看和编辑配置。
- 保存配置。
- 手动 reload。
- 查看查询日志。
- 实时接收查询日志更新。

配置保存后不应隐式改变正在运行的解析行为，除非用户明确触发 reload。

### 3.8 多进程运行

系统可选支持多进程模式，用于提高吞吐和隔离工作负载。

多进程模式下：

- 主进程负责监听器、WebUI、worker 管理和前置缓存。
- worker 负责执行实际 DNS 处理流程。
- 共享的域名/IP 标签数据应由主进程准备，再以可复用方式提供给 worker。
- worker 中的内部解析请求需要能回到主进程协调完成。
- 查询日志需要能从 worker 回传到主进程，供 WebUI 展示。

## 4. 主要处理过程

### 4.1 启动过程

启动时系统按以下顺序工作：

1. 读取配置文件。
2. 校验配置完整性和引用关系。
3. 初始化日志和运行时参数。
4. 加载并校验插件配置。
5. 初始化插件和插件注册表。
6. 构建上游 nameserver、upstream 和 upstream group。
7. 构建规则引擎和调度器。
8. 构建统一 DNS 请求处理流程。
9. 启动 UDP/TCP DNS listener。
10. 如启用 WebUI 或 DoH，则启动 HTTP 服务。

如果配置指定多进程运行，则主进程还需要创建共享标签资源、启动 worker pool，并把查询分发给 worker。

### 4.2 单次 DNS 查询过程

一次普通 DNS 查询的主流程：

1. 客户端发送 DNS 查询。
2. listener 解析请求，并记录客户端地址和 listener 名称。
3. 系统校验请求是否合法。
4. 创建请求上下文，保存请求、标签、元数据、插件上下文和最终响应状态。
5. 执行请求阶段插件。
6. 如果插件要求丢弃请求，则不返回 DNS 响应。
7. 如果插件已经生成最终响应，则跳过上游查询。
8. 如果仍需上游查询，则根据请求标签和查询类型匹配规则。
9. 根据规则选择 upstream group 和调度策略。
10. 调度器请求一个或多个上游目标。
11. 每个上游结果返回后，执行上游响应阶段插件。
12. 调度器选出最终上游结果。
13. 若还没有最终响应，则从上游结果生成最终响应。
14. 执行响应阶段插件，对最终结果进行缓存写入、过滤、替换、测速排序或记录清洗。
15. 统一整理最终 DNS answer 和 DNS response，确保二者一致。
16. 执行观测阶段插件，如查询日志。
17. 把响应返回给 listener。
18. 执行收尾阶段插件，清理 pending 状态或释放临时资源。

### 4.3 插件短路行为

插件可以影响主流程：

- 丢弃请求：当前查询不再继续处理，也不返回普通 DNS 响应。
- 停止处理：跳过后续请求或响应插件，用当前结果收敛响应。
- 设置最终响应：后续可以直接进入响应阶段，不再访问上游。
- 修改标签：影响规则选择或后续响应处理。
- 修改上游结果：影响最终返回的地址、记录内容或响应摘要。

短路语义必须清晰稳定，否则缓存、拦截、重定向和日志插件容易互相影响。

### 4.4 内部解析过程

部分插件需要在处理一个请求时发起子查询，例如重定向插件或 ECH 插件。

内部解析应满足：

- 可以指定新的域名和查询类型。
- 复用当前请求的客户端信息和 listener 信息。
- 能检测递归调用，避免无限循环。
- 有最大嵌套深度限制。
- 不应完整重跑所有插件 hook，避免不可控副作用。
- 在多进程模式下，worker 的内部解析应能通过主进程协调完成。

## 5. 数据流说明

### 5.1 请求数据

请求数据从协议层进入系统后，应统一转换为内部 DNS 消息对象。整个处理过程中只维护一个请求上下文，用于保存：

- 原始请求。
- 客户端来源。
- listener 名称。
- 请求标签。
- 匹配到的规则和上游组。
- 最终响应。
- 插件扩展上下文。
- 上游返回结果列表。
- 处理过程中的元数据。

### 5.2 标签数据

标签是分流和响应处理的关键输入。

标签来源包括：

- 域名标签文件。
- IP 标签文件。
- 插件根据请求或响应动态追加的标签。

标签分两类：

- 请求标签：规则选择主要依赖它。
- 上游结果标签：响应阶段插件主要依赖它。

迁移时要保留这两类标签的区别。不要把上游响应之后才知道的标签用于已经完成的规则选择。

### 5.3 响应数据

响应处理应区分两个概念：

- DNS answer：便于插件按记录类型、TTL、rrset 等信息处理。
- DNS response：最终返回给客户端的完整 DNS 消息。

插件可以修改 answer 或 response，但系统最终必须确保二者一致，并保证返回给客户端的响应 ID 与原始请求匹配。

### 5.4 查询日志数据

查询日志应在最终响应确定后记录。日志至少包含：

- 查询时间。
- 域名。
- 查询类型。
- listener。
- 响应码。
- 结果摘要。
- 命中的上游。
- 上游耗时。

内部解析不应默认写入普通查询日志，避免日志噪声和递归观测混乱。

## 6. 插件功能说明

当前系统内置插件能力可概括为：

| 插件能力 | 说明 |
| --- | --- |
| 标签识别 | 根据请求域名、CNAME、响应 IP、HTTPS hints 等追加标签 |
| 缓存 | 缓存正常响应，并合并相同请求的并发处理 |
| 查询日志 | 记录最终查询结果并提供 WebUI 展示 |
| 静态响应 | 按标签直接返回指定 A/AAAA 或空响应 |
| 重定向 | 按域名映射执行子查询，并返回 CNAME 加目标结果 |
| IP 过滤 | 根据 IP 标签保留或删除响应中的地址 |
| IP 替换 | 按规则把响应地址替换到目标地址段 |
| 测速 | 对候选 IP 测速，并按结果筛选返回地址 |
| HTTPS 清洗 | 删除或调整 HTTPS 记录中的特定参数 |
| ECH 注入 | 按标签给 HTTPS 响应补充 ECH 参数 |
| 示例扩展 | 演示插件如何注册上下文、自定义 resolver 或响应构造器 |

移植时不一定要一次实现全部插件，但主流程应保留足够扩展点，让这些能力可以以插件形式逐步恢复。

## 7. 移植时建议保留的核心能力

最小可用版本建议保留：

- UDP DNS listener。
- 单一配置文件。
- 基础配置校验。
- 至少一种上游 DNS 协议。
- upstream 和 upstream group。
- 默认上游组。
- 规则匹配。
- 至少一种调度策略。
- 请求上下文。
- 请求阶段、上游响应阶段、响应阶段插件 hook。
- 标签机制。
- 最终响应收敛逻辑。

增强版本再逐步加入：

- TCP DNS。
- DoH。
- WebUI。
- 缓存插件。
- 查询日志插件。
- IP 过滤、IP 替换、测速等响应增强插件。
- 多进程模式。

## 8. 可裁剪项

为了方便移植，可以暂时裁剪：

- 多种 DoH 客户端实现，只保留一种成熟实现。
- DNSCrypt、DoQ、DoT 等高级上游协议。
- WebUI 的配置编辑器，只保留状态页或 API。
- 多进程模式。
- 高级 HTTPS/ECH 处理。
- 复杂测速策略。

不建议裁剪：

- 单一配置文件和配置校验。
- 请求上下文。
- 标签机制。
- 规则分流。
- 插件 hook 阶段。
- 响应最终收敛。

这些是项目可扩展性的基础。

## 9. 关键行为约束

迁移或重写时应保持以下行为：

- DNS 接入层不包含业务决策。
- 配置错误应在启动或保存时尽早暴露。
- 插件顺序应可控。
- 请求标签先于规则选择产生。
- 上游结果标签只影响后续响应处理，不反向影响已完成的规则选择。
- 同一请求只能有一个最终响应。
- 被插件丢弃的请求不应继续访问上游。
- 最终返回响应必须与原请求 ID 对齐。
- 查询日志应记录最终结果，而不是中间状态。
- 插件私有状态应放在插件上下文中。
- reload 不应静默改变 listener 或 WebUI 地址；这类变更应要求重启。

## 10. 验收清单

移植后的系统至少应通过以下场景验证：

- 配置文件缺少必要对象时启动失败。
- 配置引用不存在对象时启动失败。
- 普通 A/AAAA 查询可以通过默认上游组返回结果。
- 标签命中后可以选择不同规则。
- 未命中规则时使用默认上游组。
- 竞速调度能返回最快成功结果。
- 等待全部调度能保留全部上游结果供插件使用。
- 请求阶段插件可以直接生成响应并跳过上游。
- 响应阶段插件可以修改最终响应。
- 缓存命中不访问上游。
- 查询日志记录最终响应码和结果摘要。
- 内部解析能返回结果，并能阻止递归。
- reload 后新配置生效；listener/WebUI 地址变化时要求重启。
